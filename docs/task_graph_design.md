# Task Graph Design

## الهدف

يوفر Task Graph تمثيلًا حتميًا للأهداف متعددة الخطوات داخل Nabdcode. كل مهمة هي عقدة مستقلة ذات تبعيات صريحة، ودور تنفيذ محدد، وإصدار خطة مرتبط بها. لا يسمح الرسم البياني بتنفيذ عقدة قبل اكتمال متطلباتها، ولا يسمح بأي تنفيذ تغييري خارج تفويض Plan/Apply القائم.

## نموذج العقدة

كل عقدة تحتوي على `task_id` ثابت وفريد، ووصف قابل للتدقيق، وقائمة `depends_on`، ودور من الأدوار المعروفة (`research`, `review`, `implement`)، وحالة تشغيل، وإصدار الخطة، ومرجع اختياري إلى الأدلة الناتجة. لا تُقبل حقول تنفيذية غير معروفة بصمت؛ الحقول الإضافية تُرفض أو تُهمل فقط عند حدود الإدخال الموثقة.

## الحالات

| الحالة | المعنى |
|---|---|
| `pending` | العقدة معرفة لكنها تنتظر اكتمال التبعيات |
| `ready` | جميع التبعيات مكتملة ويمكن ترشيح العقدة للتنفيذ |
| `running` | يجري تنفيذ العقدة داخل دورة تشغيل واحدة |
| `blocked` | لا يمكن تنفيذها بسبب تبعية فاشلة أو تفويض غير صالح |
| `completed` | اكتمل التنفيذ مع دليل نجاح قابل للتتبع |
| `failed` | فشل التنفيذ، ولا تُعاد المحاولة تلقائيًا دون قرار صريح |

## قواعد الأمان والحتمية

يجب رفض المعرفات الفارغة أو المكررة، والاعتماديات الذاتية، وأي اعتماد على عقدة غير موجودة. يجب كشف الدورات عند الإضافة وعند تحميل الرسم كاملًا. لا يجوز للعقدة `ready` أن تصبح `running` إلا إذا كان `plan_revision` مساويًا لإصدار الخطة الحالية، وكان دورها معروفًا، وكانت موافقة التنفيذ متاحة للعقد التي تتطلب تغييرات. الفشل يغلق المسار التابع: العقد التابعة لعقدة `failed` تصبح `blocked` بدل تنفيذها تخمينيًا.

## التكامل مع Plan/Apply والأدلة

يُنشأ الرسم أو يُحدّث في مرحلة Plan، وتُسجل نسخته ضمن سجل الخطة. `/apply` لا ينفذ الرسم تلقائيًا؛ بل يجيز فقط العقد الجاهزة المرتبطة بإصدار الخطة والمراجعة الحاليين. كل انتقال حالة يسجل `task_id` و`from_status` و`to_status` ووقت الانتقال وسبب القرار و`evidence_ids`. لا تُعتبر العقدة `completed` دون دليل نجاح صريح.

## الواجهة الأولية

تُقدم طبقة Python حتمية قابلة للاختبار أولًا. الواجهة الدنيا هي `add_task`, `get_task`, `mark_running`, `mark_completed`, `mark_failed`, `ready_tasks`, `blocked_tasks`, و`to_dict`. واجهة الأوامر ستُضاف لاحقًا بعد استقرار النموذج، وتبدأ بـ `/tasks` للعرض فقط حتى تُراجع سياسة التنفيذ.

## قرار التنفيذ

سيُنفذ النموذج في وحدة مستقلة `core/task_graph.py` مع اختبارات وحدات منفصلة. لن يُعاد استخدام DAG القديم الخاص بعقد التشغيل الطرفية، لأن ذلك المسار يملك عقدًا تنفيذية مختلفة وعقدة Terminal ذات سلوك خاص بالموافقة. يمكن إضافة محول لاحقًا بعد ثبات العقد العام.

## واجهة الأوامر المقيدة

يوفر الأمر `/tasks` واجهة تشغيل لحالة الرسم فقط؛ لا يشغل أدوات النظام أو يطبّق تعديلات على الملفات. الصيغ المدعومة موضحة أدناه.

| الأمر | الشرط | الأثر |
|---|---|---|
| `/tasks` أو `/tasks show` | لا شيء | يعرض العقد وحالاتها وأدوارها وتبعياتها |
| `/tasks ready` | وجود رسم حالي | يعرض العقد المستوفية لتبعياتها |
| `/tasks add <id> <role> <description> [--depends id,id]` | `PLAN` فقط | ينشئ عقدة مرتبطة بإصدار الخطة الحالي |
| `/tasks start <id> <role>` | `PLAN` أو `APPLY` | ينقل عقدة جاهزة إلى `running` عبر بوابة الصلاحية المركزية |
| `/tasks complete <id> <evidence-id> [...]` | العقدة `running` | يكمل العقدة مع أدلة إلزامية ويحرر التابعين الجاهزين |
| `/tasks fail <id> <reason>` | العقدة `running` | يسجل الفشل ويحجب التابعين |

لا يمكن لـ `implement` أن يبدأ أو يكتمل إلا إذا كان Apply مفوضًا لإصدار الخطة الحالي. يتحقق الأمر `start` من تطابق role المرسل مع role العقدة. تسجل جميع التحولات التي تتم عبر الواجهة في `plan_audit` مع إصدار الخطة وبيانات التدقيق اللازمة.
